==================================================
 技術説明トーク集（面接・プレゼン用）
 2.5D 惑星重力アクションゲーム
==================================================

このゲームの技術を人に説明するための要点まとめ。
各トピック「30秒トーク」＋「箇条書きの要点」で構成。


==================================================
1. ゲーム全体（一番最初に話す概要）
==================================================

【30秒トーク】
・マリオギャラクシー風の惑星重力と、リトルナイトメア風の2.5Dカメラを
  組み合わせたクォータービューのアクションゲーム。
・技術の核は「重力システム」「形状ベースの当たり判定」「カメラ制御」の3本柱。

【要点】
・プレイヤーの「下」は固定ではなく、近くの惑星に応じて動的に変わる
・当たり判定はタイル方式ではなく、形状同士の重なりで押し戻す方式
・カメラがゲーム性の中心


==================================================
2. 重力システム（最大の売り）
==================================================

【30秒トーク】
・複数の惑星の引力を距離で重み付けして合成し、一番強い惑星（支配惑星）の
  面法線を「プレイヤーの上方向」に採用する。
・球惑星は中心へ、箱惑星は一番近い面へ引っ張られる。
・物理用の上方向は即スナップ、見た目用はSlerpで補間と分離して、
  判定の正確さと演出の滑らかさを両立させた。

【要点】
・「電場方式」で複数惑星の重力を合成
・惑星形状は2種類：球（中心へ引力）／箱（最近接面の法線へ引力）
・箱は各面ごとに重力モードを設定でき、パズルが作れる
・上方向を2つ持つ
   - m_upDir（物理用）= 即スナップ → 判定がズレない
   - m_upDirVisual（見た目用）= Slerp補間 → モデルがなめらかに回る
・補間はフレームレート非依存（1 - pow(1-speed, dt*60)）


==================================================
3. 当たり判定（形状ベースの押し戻し）
==================================================

【30秒トーク】
・タイルではなく形状ベース。球とAABBの最近接点を求めて、めり込み量だけ
  押し戻すので角でも安定する。
・OBB（回転した箱）も地形のローカル空間で解くことでAABBと同じコードで処理できる。

【要点】
・プレイヤー＝球（上下2つの球のカプセル）、地形＝AABB / OBB / 球
・最近接点を求めて押し出す → 角でも斜めに押し出され、端のめり込みなし
・OBBはローカル空間に射影して解く → 回転対応が自動で効く
・レイは「接地判定と地面法線の取得」だけに使う
・押し出し方向が上向き寄りなら床、横向きなら壁と分類


==================================================
4. カメラ（2.5D / リトルナイトメア風）
==================================================

【30秒トーク】
・プレイヤーを追従しつつ、ルーム単位で構図を切り替え、重力方向に合わせて
  カメラ自身も傾く。

【要点】
・ルームベース：マップを部屋単位で区切り、部屋の中心を基準に構図を作る
・部屋をまたぐと中心をブレンド補間して切り替え
・重力（upDir）に合わせてカメラもロール（傾く）
・カメラシェイク、惑星到達ズーム、浮遊などの演出


==================================================
5. シェーダー拡張（元はLambert+Blinn-Phong）
==================================================

【30秒トーク】
・元のフレームワークはLambert+Blinn-Phongの素朴なライティング。
・そこを、太陽光はトゥーンで3段階に量子化、点光は物理ベースのCook-Torrance GGX
  というハイブリッドに拡張した。
・影はPCSSで接地は鋭く遠方は柔らかく。色はACESトーンマッピング。
・惑星の地面はトリプレーナー＋重力の上方向に応じた芝ブレンドで、
  重力システムと描画を連動させている。
・輪郭線はキャラがインバーテッドハル、地形が深度ベースのエッジ検出の2方式。

【要点】
・ライティング＝PBR×トゥーンのハイブリッド
   - 平行光（太陽）→ トゥーン（3段階に量子化したフラットな陰影）
   - 点光 → 物理ベース PBR（Cook-Torrance GGX）
・影＝PCSSソフトシャドウ
   - ブロッカー検索 → 半影サイズ推定 → Poissonディスク16点でPCF
   - 接地はくっきり、離れるほど柔らかくボケる
・色調＝ACESフィルミックトーンマッピング（白飛び抑制）
・惑星の地面表現（重力と連動）★独自性が高い
   - トリプレーナーマッピング（UVを使わず3軸投影）
   - 重力の上方向に応じて芝・芝法線・境目テクスチャをブレンド
   - 球惑星は「中心→ピクセル」を法線にして完全に滑らかな陰影
・宇宙の質感：リムライト、擬似環境反射、半球環境光


==================================================
6. アウトライン（輪郭線・2方式）
==================================================

【30秒トーク】
・輪郭線はキャラと地形で方式を使い分けている。
・キャラはインバーテッドハル（モデルを膨張させ裏面だけ描く）、
  地形は深度バッファからのエッジ検出。

【要点】
・A. インバーテッドハル方式（キャラ用 / 原神風）
   - モデルを法線方向に膨張させ、前面カリングで裏面だけ描く
   - 溶接した平均法線(smoothNormal)で膨張 → 板割れ防止
   - ビュー空間で一定ワールド幅押し出し → 距離補正（遠いと細く）
   - スキニング対応でアニメに追従
   - 深度バイアスで継ぎ目に線が出ないようにする
・B. ポストプロセス・エッジ検出方式（地形/全体用）
   - 深度の2階差分でシルエット、復元法線の食い違いで角を検出
   - 面一に連続した面（継ぎ目）は線が出ない


==================================================
7. 頂点シェーダー（Vertex Shader）
==================================================

【30秒トーク】
・頂点シェーダーは頂点ごとに並列実行され、ローカル→ワールド→ビュー→射影の
  4段で座標変換し、同時にピクセルシェーダー用のワールド法線やTBN基底を準備する。
・用途別に通常・半透明・影生成・輪郭の4種を用意し、半透明と影生成にもスキニングを
  入れて発光と影をアニメに追従させた。輪郭線のVSは新規に自作。

【要点】
・役割は2つ：頂点の座標変換 ＋ ピクセルシェーダー用データの準備
・座標変換：ローカル → ワールド → ビュー → 射影
・TBN基底（法線・接線・従法線）を準備 → 法線マッピング用
・出力値はピクセル間で自動補間されてPSへ渡る
・4種類のVSの使い分け
   - VS_Lit（通常）：変更なし（元のまま）
   - VS_UnLit（発光）：スキニングを追加 ★
   - VS_GenDepthMap（影）：スキニングを追加 ★
   - VS_Outline（輪郭）：新規自作 ★★


==================================================
8. スキニング（重要）
==================================================

【30秒トーク】
・スキニングは、1枚のつながったメッシュを骨格で変形させてキャラを動かす技術。
・各頂点が最大4本の骨に所属度（ウェイト）を持ち、頂点シェーダーで骨の行列を
  ウェイトで加重平均して頂点と法線を変形する（線形ブレンドスキニング）。
・本体・発光・影・輪郭すべてで同じスキニングを揃えないとズレるので、
  各パスのVSに実装している。

【要点】
・1枚の継ぎ目のないメッシュを内部の骨格で動かす
・1頂点が複数の骨に所属（skinIndex＝骨番号、skinWeight＝影響度、合計1.0）
・骨の行列をウェイトで加重平均 → 頂点と法線を変形
・法線も変形しないと陰影がおかしくなる
・計算はGPU（頂点シェーダー）が並列で処理
・別名 LBS（線形ブレンドスキニング）
・自分の手柄＝「スキニングを発明」ではなく
  「既存のスキニングを発光・影・輪郭の全パスに展開して整合させた」


==================================================
9. アニメーション（node → 動き）
==================================================

【30秒トーク】
・モデルは親子構造のノード（骨）の集まりで、アニメはノードごとに時間つきの
  キー（位置・回転・拡縮）を持つ。
・毎フレーム、現在時刻の前後キーを二分探索して、位置はLerp・回転はSlerpで補間し、
  各ノードのローカル行列を作る。
・次にルートから再帰的に親のワールド行列を掛けて、肩を動かすと肘や手が連動する
  階層変形にする。
・最後に逆バインド行列と合成してボーン行列を作り、頂点シェーダーへ送ってスキニング。

【要点】
・モデル＝親子構造のノード（骨）の木構造
・アニメデータ＝ノードごとの時間つきキー（位置・回転・拡縮の3チャンネル）
・毎フレームの処理
   1. 二分探索で現在時刻の前後キーを探す
   2. 位置・拡縮はLerp、回転はSlerpで補間 → ローカル行列
   3. ルートから再帰で親のワールド行列を掛ける → 親の動きが子に伝播
   4. 逆バインド行列 × ワールド行列 → ボーン行列 g_mBones[]
・データの流れ
   glTF読込 → ノード木 → 補間 → 階層合成 → スキニング


==================================================
10. DrawVertices（即時描画）
==================================================

【30秒トーク】
・DrawVerticesは、あらかじめ作った頂点バッファを使うモデル描画と違い、
  CPU側の頂点配列をその場でGPUに送って即描画する関数。
・デバッグ線・スプライト・ポストプロセスの全画面ポリゴンなど、
  毎フレーム形が変わる使い捨ての頂点に使う。

【要点】
・CPUが渡すもの＝「行列（定数バッファ）」＋「頂点配列（一時バッファ）」
・実際の「頂点×行列」の計算はGPUの頂点シェーダーが並列で行う
・topology（点/線/三角形の繋ぎ方）、stride（頂点1個のバイト数）を指定
・DISCARD方式の動的バッファに毎回書き込む
・DrawVertices vs DrawMesh(DrawIndexed)
   - DrawVertices：毎回CPUから送る一時バッファ。使い捨ての形用
   - DrawMesh：読込時に作る固定バッファ（GPU常駐）。3Dモデル用


==================================================
11. レンダリングパイプライン（GPUに送った後→画面）
==================================================

【30秒トーク】
・Drawを呼ぶと、入力アセンブラが頂点を組み立て、頂点シェーダーが頂点ごとに
  並列で座標変換する。
・次にラスタライザが三角形をピクセルに分解し、頂点の出力値を各ピクセルへ補間。
・ピクセルシェーダーがピクセルごとに並列でライティングして色を決め、
  出力マージャが深度テストとブレンドを経てレンダーターゲットに書き込む。
・最後にPresentで画面に表示。自分で書けるのは頂点とピクセルのシェーダーだけ。

【要点（5段パイプライン）】
・① 入力アセンブラ：頂点を組み立て（GPU固定機能）
・② 頂点シェーダー：頂点ごとに並列で座標変換（自分で書ける）
・③ ラスタライザ：三角形をピクセルに分解＋頂点出力を補間（固定機能）
・④ ピクセルシェーダー：ピクセルごとに並列で色計算（自分で書ける）
・⑤ 出力マージャ：深度テスト・ブレンドして書き込み（固定機能）
・→ Present（スワップチェーン）で画面表示
・核心：自分で計算を書けるのは②VSと④PSだけ。間は固定機能が自動処理

 役割分担の早見表
==================================================
・CPU  ：行列を作る、頂点を用意、GPUへ送る、描画命令を出す

   と言うと正確で誠実な印象になる。

12. deltatime（デルタタイム）
==================================================

【30秒トーク】
・deltatimeは「前のフレームから今のフレームまでに経った時間（秒）」。
・移動などに掛けることで、FPSが違っても実時間で同じ速さに保てる。
・例えば速度に掛ければ、60FPSでも30FPSでも1秒で進む距離が同じになる。
・このゲームでは dt60 = GetDt() × 60 という形で「60FPS換算で何フレーム
  進んだか」として使い、重力や回転補間をFPS非依存にしている。
・処理落ち時に値が大きくなりすぎないよう上限（0.05秒）でクランプして、
  壁のすり抜け事故を防いでいる。

【要点】
・deltatime ＝ 1フレームの経過時間（秒）。60FPSなら約0.0166秒
・移動に掛ける：x += 速度 × deltatime → 1秒で進む量が一定
・なぜ必要：掛けないとPC性能（FPS）でゲーム速度が変わってしまう
・フレームドロップ時はdeltatimeが大きくなる → その回に多めに加算して
  実時間での進み方を一定に保つ
・dt60テクニック：GetDt() × 60 で「60FPS基準で何フレーム分か」
   - 60FPS → dt60 = 1.0 ／ 30FPS → dt60 = 2.0 ／ 120FPS → dt60 = 0.5
   - 60FPS基準で数値を調整 → 最後に ×dt60 するだけでFPS非依存
・上限クランプ（最大0.05秒）：カクついても一気に大量加算せず、
  キャラが壁をすり抜けるテレポート事故を防ぐ
